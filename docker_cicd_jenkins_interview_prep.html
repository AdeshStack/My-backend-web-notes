Docker Fundamentals
#001

What is Docker and why is it used?

Docker is a containerization platform that packages an application together with its dependencies, libraries and configuration into a single, portable unit called a container. It solves the classic “it works on my machine” problem because the container runs identically on a laptop, a CI server, or production.

#002

What is a Container?

A container is a lightweight, isolated runtime instance created from an image. It shares the host machine's OS kernel but has its own filesystem, process space, and network interface, which makes it much lighter and faster to start than a virtual machine.

#003

What is an Image?

A Docker image is a read-only template that contains the application code, runtime, libraries and settings needed to run it. Images are built in layers, and containers are simply running instances created from an image.

#004

Difference between an Image and a Container?

An image is the static blueprint (like a class), while a container is a running instance of that image (like an object). You can create many containers from the same image, each with its own writable layer and lifecycle.

#005

Difference between a Virtual Machine and a Container?

A VM virtualizes the hardware and runs a full guest OS with its own kernel, which makes it heavier and slower to boot. A container shares the host OS kernel and only isolates the process, filesystem and network, so it starts in seconds and uses far less memory/disk.

#009

Difference between CMD and ENTRYPOINT?

ENTRYPOINT defines the fixed command that always runs when the container starts, while CMD supplies default arguments that can be easily overridden at `docker run`. A common pattern is ENTRYPOINT ["java","-jar","app.jar"] with CMD used only for optional default arguments.

Dockerfile & Images
#010

What is a multi-stage Docker build and why use it?

A multi-stage build uses multiple FROM statements in one Dockerfile — one stage compiles/builds the app (e.g. with the full Maven + JDK toolchain), and a final, much smaller stage (e.g. a slim JRE) copies over only the built artifact. This keeps the final production image small and avoids shipping build tools, source code or secrets.

Similar to .gitignore, .dockerignore excludes files (like .git, target/, node_modules, local .env files) from the build context, which makes builds faster and prevents accidentally baking secrets or unnecessary files into the image.

#012

How do you optimize a Docker image (layer caching, image size)?

Order instructions from least to most frequently changing (e.g. copy pom.xml and run dependency resolution before copying source code) so Docker's layer cache is reused across builds. Use slim/alpine base images, multi-stage builds, and combine related RUN commands to reduce the number of layers and final image size.

What is image tagging and why does it matter in production?

#027

Why doesn't 'localhost' work between two containers?

Inside a container, `localhost` always refers to that same container, not the host machine or a sibling container. To reach another container you must use its container/service name over a shared Docker network, or the host's actual IP.

#029

What is a Volume in Docker and why use it?

A volume is Docker-managed storage that persists data outside the container's writable layer. Since containers are ephemeral, anything written inside them is lost when the container is removed — volumes (or bind mounts) keep data like database files safe across container restarts/recreation.

Port mapping exposes a container's internal port on the host machine so external clients can reach it, using the -p flag: `docker run -p 8080:8080 image-name` maps host port 8080 to container port 8080.

Deployment Strategies
#058

What is Blue-Green deployment?

Blue-Green deployment keeps two identical production environments (Blue = current live, Green = new version). Traffic is switched from Blue to Green only once Green is verified healthy, giving near-zero downtime and an instant rollback (just switch traffic back to Blue).
My rating: Not rated
Deployment Strategies
#059

What is a Rolling deployment?

A rolling deployment gradually replaces old instances with new ones a few at a time, so the application stays available throughout, though both versions run simultaneously for a short period.
My rating: Not rated
Deployment Strategies
#060

What is Canary deployment?

Canary deployment releases the new version to a small subset of users/traffic first, monitors metrics/errors, and only rolls it out to everyone once it's proven stable — reducing the blast radius of a bad release.

Deployment Strategies
#061

How would you roll back a bad production deployment?

With Blue-Green, roll back by switching traffic back to the previous (still-running) environment instantly. With rolling/canary deployments, redeploy the last known-good, tagged image/artifact through the same pipeline used to deploy the bad one, keeping the process auditable and repeatable.

#064

A Jenkins pipeline suddenly starts failing at the Docker build stage only in CI, but works locally — how do you debug it?

Check for environment differences first: is the Jenkins agent's Docker daemon version different, is the build using a stale layer cache, are required build args/secrets missing on the agent, or is disk space low on the agent. I'd reproduce by SSHing into the agent (or running the exact same `docker build` command Jenkins runs) to isolate whether it's a pipeline configuration issue or an environment issue.
